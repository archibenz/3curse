# Теория для защиты: Locator Tracker

> Шпаргалка к презентации. Каждый раздел соответствует слайду.
> Привязка к коду: `locator-tracker/apps/api/src/services/*.ts`

---

## 0. Что мы вообще сделали (одним абзацем)

Мы построили **SaaS-платформу для визуального регрессионного тестирования веб-интерфейсов**, которая сама находит изменения между двумя версиями страницы и **предлагает новый CSS-селектор** вместо сломанного в тесте. Вместо попиксельного сравнения картинок или хрупких селекторов мы сравниваем **интерактивные элементы DOM** по пяти группам признаков, используем **глобальный алгоритм назначения** (Венгерский / Куна–Манкреса), а затем **калибруем уверенность решения** — автообновить, предложить на ревью или оставить человеку.

Стек: Next.js 15 (фронт), Fastify + Prisma + Postgres + Redis (бэк), Playwright (браузер-движок), BullMQ (очередь сканов), TypeScript везде.

---

## СЛАЙД 1 — Название и команда

**Тема:** «Метод глобального сопоставления элементов веб-страницы для автоматизированного выявления регрессионных изменений интерфейса».

**Что за словами:**
- «Глобальное сопоставление» — решение принимается для всех элементов сразу как задача оптимального назначения, а не жадно для каждого.
- «Регрессионные изменения» — непреднамеренные или ожидаемые изменения UI, которые ломают существующие UI-тесты (селекторы перестают находить нужные элементы).

---

## СЛАЙД 2 — Актуальность

**Проблема:**
1. **Попиксельное сравнение** (Percy, Applitools в базовом режиме) — ломается при изменении шрифта, сглаживания, антиалиасинга, тем оформления. Даёт огромный шум.
2. **Жёсткие CSS-селекторы** (`.btn-primary-v2`, `#submit-button-42`) — ломаются при любом рефакторинге вёрстки, миграции на Tailwind/CSS-in-JS.
3. **Локальные жадные сопоставления** — если первая пара сопоставлена неверно, все последующие тоже расходятся (каскад ошибок).

**Цифра для аргументации:** в индустрии 30–50% времени QA уходит на обслуживание сломанных тестов (Google Testing Blog, Microsoft Research).

**Наш ответ:** метод, устойчивый к визуальному шуму, рефакторингу и перестановкам — с понятным объяснением каждого решения.

---

## СЛАЙД 3 — Объект и предмет

- **Объект:** процесс автоматизированного выявления регрессионных изменений UI веб-приложений.
- **Предмет:** методы и алгоритмы сопоставления элементов DOM между версиями страницы.

**Ключевая фраза для жюри:** «Мы решаем задачу не по одному признаку, а по пяти группам сразу, с глобальным назначением и калибровкой уверенности». Это выделяет нас от конкурентов, которые делают одно из трёх (пиксели / DOM-tree / ML).

---

## СЛАЙД 4 — Существующие подходы (и почему они не подходят)

| Подход | Проблема |
|---|---|
| **Попиксельное сравнение** (pixel-diff) | Чувствительно к рендерингу, шрифтам, анимациям, тёмной теме, динамическим данным |
| **Сравнение DOM-деревьев** (tree edit distance, Zhang-Shasha) | Сложность O(n³–n⁴), плохо масштабируется на реальные страницы с 500+ элементами |
| **CSS-селекторы по id/class** | Хрупкость при рефакторинге, переименовании классов (особенно в Tailwind) |
| **ML-подходы** (CNN на скриншотах) | Нужны тысячи размеченных пар, плохо интерпретируются, «чёрный ящик» |

**Общий недостаток:** узкий набор признаков + локальная жадная стратегия → каскадные ошибки.

## СЛАЙД 5 — Этапы нашего метода

Пайплайн (код: `apps/api/src/workers/scan.processor.ts` → `ScanOrchestrator.ts`):

1. **Извлечение DOM и геометрии** — Playwright открывает страницу, JS-скрипт в браузере достаёт все интерактивные элементы (`button`, `input`, `a`, `[role=…]`, `[data-testid]`), их bbox, атрибуты, текст, путь в DOM.
   Код: `PlaywrightEngine.ts`.

2. **Построение вектора признаков** (fingerprint) для каждого элемента — 5 групп (см. слайд 6).
   Код: `FingerprintEngine.ts` → `calculateMatchScore()`.

3. **Матрица стоимости** — для каждой пары (baseline-элемент × current-элемент) считается взвешенный score сходства. Получается матрица N×M.

4. **Глобальное назначение** — ищем оптимальное паросочетание в двудольном графе (Венгерский алгоритм). Результат — однозначное соответствие «какой старый элемент стал каким новым».

5. **Калибровка уверенности** — каждому сопоставлению приписывается уровень (HIGH / MEDIUM / LOW) и тип изменения (SELECTOR_CHANGE / CONTENT_CHANGE / POSSIBLY_REMOVED / REMOVED).
   Код: `ScanOrchestrator.ts` → `findBestMatch()`.

**Итог:** не «что-то поменялось», а «элемент X (кнопка “Submit”) теперь имеет селектор Y, уверенность 0.87, рекомендуем автообновить».

## СЛАЙД 6 — Пять групп признаков

Код: `FingerprintEngine.ts` — функция `calculateMatchScore()`.

| Группа | Вес | Что включает |
|---|---|---|
| **Текст** | 0.32 | Видимый текст элемента, placeholder, aria-label |
| **Атрибуты** | 0.32 | `data-testid`, `id`, `name`, `class`, `role`, `type` |
| **Структура** | 0.18 | Родитель, дед, позиция среди соседей, соседний текст |
| **Семантика тега** | 0.12 | HTML-тег + иерархия близости (BUTTON ≈ A ≈ [role=button]) |
| **Геометрия** | 0.06 | Относительная площадь, позиция на странице |

**Почему такие веса:** по результатам экспериментов (см. `ALGORITHM_ANALYSIS.md`) текст и атрибуты — самые информативные. Структура и тег — стабилизаторы при перестановках. Геометрия — минимальный вес из-за responsive-дизайна (±20% вариация считается нормой).

**Ключевая формула:**
```
Score = 0.32·text + 0.32·attrs + 0.18·structure + 0.12·tag + 0.06·size
```

Если вопрос «почему не равные веса?» — ответ: данные признаков неравноценны по информативности. `data-testid` — почти однозначный идентификатор; размер — всего лишь подсказка.

## СЛАЙД 7 — Текстовое сходство

Код: `FingerprintEngine.ts` → `fuzzyMatch()`, `isDynamicContent()`, `ngramSimilarity()`.

**Три стратегии в зависимости от длины и содержимого:**

1. **Длинные строки (>20 символов)** — нормализованное **расстояние Левенштейна**:
   ```
   similarity = 1 - editDistance(a, b) / max(|a|, |b|)
   ```

2. **Короткие строки (≤20 символов)** — **комбинация** Левенштейна и биграмм (n-gram overlap, n=2):
   ```
   similarity = (levenshtein + ngram) / 2
   ```
   Зачем: «Login» и «Log In» по Левенштейну имеют похожесть ~0.6, а по биграммам — ~0.85. Для коротких строк биграммы лучше ловят смысловую близость.

3. **Динамический контент** — детектор (`isDynamicContent`) распознаёт:
   - даты (`2024-01-15`, `15.04.2026`)
   - числа и денежные значения (`$100.50`, `1 234 ₽`)
   - время (`10:30`)
   - статусы («Loading», «Done»)

   Если текст распознан как динамический → сразу даём score **0.85** (допускаем изменение, не считаем регрессией).

**Зачем это нужно:** обновление цены товара или даты не должно ломать все тесты на странице. Без этого детектора каждый скан интернет-магазина рождал бы сотни ложных срабатываний.

## СЛАЙД 8 — Атрибуты

Код: `FingerprintEngine.ts` → `getAttributeWeight()`, `matchAttribute()`, `calculateAttributeScore()`.

**Иерархия надёжности** (веса внутри группы atts=0.32):

| Атрибут | Вклад | Почему |
|---|---|---|
| `data-testid` | 0.25 | Создан специально для тестов — максимально стабилен |
| `data-cy` | 0.23 | Cypress-конвенция |
| `data-test` | 0.20 | Общая test-конвенция |
| `id` | 0.15 | Часто уникален, но может меняться при рефакторинге |
| `name` | 0.12 | Обычно стабилен в формах |
| `aria-label` | 0.10 | Человекочитаемый, связан с семантикой |
| `role` | 0.08 | Семантическая роль |
| `type` | 0.05 | У input’ов относительно стабилен |
| `class` | 0.08 | Нестабилен, поэтому fuzzy + малый вес |

**Fuzzy matching для классов** (`classNameSimilarity`):
- Разбиваем класс на токены: `"btn btn-primary btn-lg"` → `["btn", "btn-primary", "btn-lg"]`
- Ищем пересечения с fuzzy-матчингом каждого токена.
- При рефакторинге Tailwind: `btn-primary → btn-secondary` даёт ~0.7 (а не 0, как при точном сравнении).

**Почему иерархия важна:** если `data-testid` совпадает — это почти гарантированное сопоставление. Если только класс — это подсказка, но не доказательство.

## СЛАЙД 9 — Итоговая оценка и пороги

**Формула (повторяем):**
```
Score(e₁, e₂) = 0.32·text(e₁,e₂) + 0.32·attr(e₁,e₂) + 0.18·struct(e₁,e₂) + 0.12·tag(e₁,e₂) + 0.06·size(e₁,e₂)
```

**Адаптивные пороги** (`TAG_THRESHOLDS` в `FingerprintEngine.ts`):

| Тип | Порог | Логика |
|---|---|---|
| BUTTON | 0.72 | Семантически важен → требуем высокую уверенность |
| INPUT | 0.70 | Важен для форм |
| A (ссылка) | 0.68 | Средняя важность |
| DIV | 0.60 | Контейнер, часто контекст-зависим |
| LI | 0.58 | Порядок может меняться |

**Почему разные пороги:** для кнопки ошибка сопоставления дороже (сломается ключевой сценарий теста), чем для `<div>`-обёртки. Поэтому для важных элементов требуем более высокую степень сходства, чтобы снизить ложные срабатывания. Для контейнеров наоборот — смягчаем, чтобы не пропускать реальные переносы.

**Матрица стоимости** — N×M таблица score для всех пар baseline × current. Из неё дальше ищем оптимальное сопоставление.

## СЛАЙД 10 — Венгерский алгоритм (ключевой слайд!)

**Задача:** имея матрицу стоимостей C[i][j] (сходство i-го baseline элемента с j-м current элементом), найти назначение π: baseline → current, максимизирующее Σ C[i][π(i)], при условии взаимной однозначности.

Это — классическая задача **о назначениях** (assignment problem) на двудольном графе.

**Венгерский алгоритм (Kuhn 1955, Munkres 1957):**
- Сложность: **O(n³)**
- Гарантирует **оптимальное** решение (в отличие от жадного)
- Работает на прямоугольных матрицах (при N ≠ M)

**Почему это важно по сравнению с локальным (жадным) подходом:**

Пример: страница со списком из трёх кнопок [A, B, C]. После рефакторинга порядок изменён: [C, A', B] (A' — чуть изменённый A).

- **Жадный алгоритм**: берёт первое лучшее совпадение. Для A найдёт A' (ок), для B может взять C (уже «съеден»), для C — найдёт B ошибочно. Каскад.
- **Глобальный (Венгерский)**: оптимизирует сумму по всем парам. Учитывает, что «если A→A', а B→B, то C→C даёт больше суммарного сходства, чем C→B, A→C, B→A».

**Формулировка для жюри:**
«Жадная стратегия может выбрать локально лучшее решение, но глобально неоптимальное. Задача о назначениях решается за полиномиальное время венгерским алгоритмом и гарантирует максимум суммарного сходства, что устойчиво к перестановкам элементов».

**Где живёт в коде:** оптимальное сопоставление выполняется в `ScanOrchestrator.ts` при обработке `SCAN_TYPE=DEPLOY` через функцию `findBestMatch` с последующим глобальным согласованием.

## СЛАЙД 11 — Геометрическая коррекция: DBSCAN

Код: `GeometryMatcher.ts` → `detectContainerShifts()`, `clusterOffsets()`.

**Проблема:** если заголовок страницы вырос на 20px, все элементы ниже сдвинулись на 20px. Без коррекции каждый из них будет помечен как «изменилась геометрия» → шум.

**Решение:** кластеризуем векторы смещений и ищем **моду** — если 80%+ дочерних элементов контейнера сдвинулись на одинаковый вектор, значит это сдвиг контейнера, а не отдельных элементов.

**Почему DBSCAN, а не просто медиана:**
- Медиана — одна точка. Плохо, если смещений две группы (один блок сдвинулся, другой нет).
- **DBSCAN** (Density-Based Spatial Clustering) находит **все плотные кластеры** в пространстве смещений. Параметры:
  - `eps = 10px` — радиус соседства
  - `minPts = 3` — минимум точек в кластере
- Работает с шумом (outliers игнорируются).
- Не требует заранее задавать число кластеров (в отличие от k-means).

**Что даёт на практике:**
- Обнаруживает вложенные сдвиги (контейнер сдвинулся + внутри него блок тоже уехал).
- Снижает количество ложных «геометрических» изменений на 40-60% в реальных сценариях.

**Формулировка:** «Для устранения каскада ложных срабатываний при сдвиге контейнера используется плотностная кластеризация DBSCAN на векторах относительных смещений дочерних элементов».

## СЛАЙД 12 — Калибровка уверенности и типы изменений

Код: `ScanOrchestrator.ts` — решающая логика после `findBestMatch`.

**Три уровня уверенности:**

| Уровень | Score | Действие |
|---|---|---|
| **HIGH** | ≥ 0.85 | Автоматическое обновление селектора (`UPDATE_SELECTOR`) |
| **MEDIUM** | 0.72–0.85 | Рекомендация с пометкой «проверить» (`MANUAL_REVIEW`) |
| **LOW** | < 0.72 | Элемент не сопоставлен — ручной разбор или removal |

**Типы изменений (ChangeType):**

1. `SELECTOR_CHANGE` — элемент нашёлся, но CSS-селектор стал другим → предлагаем новый.
2. `CONTENT_CHANGE` — селектор тот же, но сильно изменился текст/атрибуты (score < 0.85).
3. `POSSIBLY_REMOVED` — элемент не найден с высокой уверенностью, но есть частичные совпадения (score > 0, но ниже порога).
4. `REMOVED` — совсем ничего не нашлось.

**Как это работает в продукте:**
- Пользователь видит диф в UI (`/projects/:id/diff?scan=...`): скриншот до/после, bbox, предлагаемый новый селектор, уровень уверенности.
- Для HIGH — кнопка «Apply automatically», которая патчит тестовый файл.
- Для MEDIUM — «Review and accept».
- Для LOW — просто уведомление, дальше разбирается человек.

**Важно для жюри:** мы не просто детектируем изменения, а **автоматизируем починку тестов** — экономим те самые 30-50% времени QA, о которых говорили на слайде 2.

## СЛАЙД 13 — Экспериментальная методика

**Два источника данных:**

1. **Синтетические мутации DOM** — мы программно модифицировали baseline-страницы (переименование классов, перестановка элементов, изменение текста, сдвиги геометрии). Получаем ground truth — знаем, какой элемент каким должен быть сопоставлен.

2. **Реальные сценарии** — снимки реальных сайтов в разных доменах:
   - E-commerce (каталог, корзина, чекаут)
   - SaaS-панели (дашборды, таблицы, формы)
   - Контентные сайты (блог, медиа)
   - Формы авторизации

**Типы тестируемых изменений:**
- Текстовые (переформулировки, переводы, динамические данные)
- Атрибутивные (переименование классов, data-testid)
- Структурные (перестановка, перенос в другой контейнер)
- Геометрические (сдвиги, ресайз, responsive)
- Комбинированные (всё сразу)

**Метрики качества:**
- **Precision (точность)** — доля верных совпадений среди всех предсказанных совпадений.
- **Recall (полнота)** — доля найденных совпадений из всех реальных.
- **F1-score** — гармоническое среднее precision и recall.
- **Accuracy** — общая доля верных классификаций.

## СЛАЙД 14 — Результаты

- **Средняя accuracy: ~94%** (было ~68-72% у базового подхода с локальным сопоставлением)
- **Прирост: +24%**
- **Накладные расходы: <5%** по времени обработки

**Откуда +24%:**
- Fuzzy matching атрибутов: +6%
- Ngram для текста + детектор динамического контента: +5%
- Multi-level structure (parent + grandparent): +3%
- DBSCAN вместо median для геометрии: +4%
- Type-specific thresholds: +3%
- Vengerian global matching vs greedy: +3%

**Сложные элементы (DIV, LI, SPAN)** — именно там максимальный прирост (с 48-60% до 85-90%), потому что им больше всего нужен структурный контекст.

## СЛАЙД 16 — Практика

**На реальных сценариях метод корректно обрабатывает:**

1. **Изменения текста** — «Войти» → «Вход», «Submit» → «Complete» (если это не полная замена смысла).
2. **Переименование CSS-классов** — `btn-primary` → `btn-action`, миграции на Tailwind.
3. **Перемещение элементов** — кнопка переехала из шапки в сайдбар (структура+геометрия меняются, но атрибуты и текст стабильны).
4. **Динамические данные** — цены, даты, счётчики не триггерят ложные срабатывания.
5. **Смена семантически близких тегов** — `<button>` → `<a role="button">` распознаётся как тот же элемент.

**Практический эффект:** тестовые наборы Cypress/Playwright проходят после рефакторинга UI без ручного обновления селекторов в 85%+ случаев.

## СЛАЙД 17 — Производительность и архитектура

**Бенчмарк (типичная страница, 50 интерактивных элементов):**

| Операция | Время |
|---|---|
| Fuzzy matching одной пары | 0.5 мс |
| Полная матрица 50×50 | 25 мс |
| DBSCAN кластеризация | 2 мс |
| Венгерский алгоритм на 50×50 | ~15 мс |
| **Итого на страницу** | **~45 мс** |
| Сканирование 10 страниц | ~500 мс |

**Для сравнения:** попиксельное сравнение той же страницы — 200-300 мс (ImageMagick diff), при этом без семантики.

**Архитектура (модульная, это важно для жюри):**

```
┌─────────────────┐
│ PlaywrightEngine│  ← headless браузер, снимает DOM + скриншоты
└────────┬────────┘
         ↓
┌─────────────────┐
│FingerprintEngine│  ← считает 5-компонентные векторы признаков
└────────┬────────┘
         ↓
┌─────────────────┐
│ GeometryMatcher │  ← DBSCAN, container shifts
└────────┬────────┘
         ↓
┌─────────────────┐
│ScanOrchestrator │  ← Венгерский алгоритм, классификация изменений
└────────┬────────┘
         ↓
┌─────────────────┐
│    Postgres     │  ← сканы, элементы, изменения, baseline-ы
└─────────────────┘
```

Очередь BullMQ (на Redis) позволяет запускать сканы параллельно. CI/CD-вебхуки GitHub/GitLab/Jenkins запускают DEPLOY-сканы автоматически после пуша/деплоя.

# 💡 Часто задаваемые вопросы (подготовьтесь к ним)

### В1. Почему Венгерский, а не современные нейросети?
Венгерский алгоритм — **оптимален и интерпретируем**. Нейросеть дала бы сопоставимое или лучшее качество, но:
1. Нужны тысячи размеченных пар (у нас их нет и в индустрии нет публичных).
2. Результат — «чёрный ящик», объяснить пользователю, почему этот элемент сопоставлен с этим — нельзя.
3. Вычислительно дороже.
Наш подход — **baseline, относительно которого можно строить ML-улучшения**, не теряя интерпретируемости.

### В2. А что если на странице 10000 элементов — Венгерский O(n³) же медленный?
На практике мы сопоставляем только **интерактивные** элементы (`button`, `input`, `a`, `[data-testid]`, `[role]`) — их обычно 50-300 на страницу. Для 300 элементов n³ ≈ 27 млн операций — это ~100 мс. Плюс есть оптимизации: разбиваем страницу на регионы, сопоставляем внутри каждого.

### В3. Как вы выбирали веса (0.32, 0.32, 0.18, 0.12, 0.06)?
Grid search на синтетическом датасете с известными парами. Исходно были равные веса по 0.20, но ablation показало, что текст и атрибуты — самые информативные, а геометрия и тег — вторичны. Окончательные веса — компромисс между accuracy и устойчивостью на разных типах страниц.

### В4. Почему не попиксельное сравнение?
Три причины:
1. **Шум**: изменение шрифта OS, сглаживание, тёмная тема → каждый пиксель разный, но UI тот же.
2. **Нет семантики**: пиксельный diff скажет «картинка изменилась», но не «кнопку Submit переименовали в Complete».
3. **Нет автопочинки**: из пикселей не вывести новый CSS-селектор для теста.

### В5. Как вы обрабатываете iframe и Shadow DOM?
В текущей версии — iframe читаются, Shadow DOM — частично (открытые). Это упомянуто в перспективах. Для большинства коммерческих проектов этого хватает.

### В6. Чем отличаетесь от Applitools / Percy?
- Они работают с **изображениями** (visual AI), мы — с **DOM-структурой**. Это дополняющие подходы, но наш даёт **actionable selector** для починки тестов.
- Мы **интерпретируемы**: каждый вклад (текст 0.294, атрибуты 0.25, …) можно показать разработчику.
- Мы **open-source-friendly** и **self-hosted** — Applitools/Percy — SaaS с подпиской и отправкой данных в США.

### В7. Насколько ваш метод «real-time»?
Скан страницы — ~500 мс вместе с Playwright. Для CI/CD это мгновенно. Для интерактивных превью в IDE (Storybook) — приемлемо с кэшированием baseline.

### В8. Что такое «matching по fingerprint» — это криптография?
Нет. Термин «fingerprint» используется в широком смысле — **вектор признаков элемента**, уникально его характеризующий в контексте страницы. Никакой хеш-функции и криптографии.

### В9. Вы реально использовали DBSCAN? Это же классический ML-алгоритм.
Да, реализация в `GeometryMatcher.ts` → `clusterOffsets()`. Упрощённая (без KD-деревьев, т.к. N маленькое), но алгоритмически это именно DBSCAN: плотностное расширение кластеров, учёт шума.

### В10. Как у вас с безопасностью (это же SaaS)?
- JWT-аутентификация с refresh-токенами.
- AES-256-GCM шифрование auth.json (данные для логина в целевой сайт) — `apps/api/src/lib/crypto.ts`.
- CSP-заголовки в Next.js.
- Валидация входных данных на каждой границе (Zod-схемы).
- Redis-раздача задач через BullMQ — никаких RCE из очереди.
