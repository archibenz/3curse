Актуальность проблемы

Проблема

  • Веб-приложения обновляются ежедневно — UI меняется быстрее, чем тесты
  • Ручная проверка регрессий — трудоемка и ненадежна
  • Попиксельное сравнение скриншотов дает ложные срабатывания при любом сдвиге
  • Существующие подходы не учитывают семантику элементов

Последствия

  • До 40% времени QA уходит на поддержку сломанных селекторов
  • Пропущенные регрессии — дефекты в продакшене
  • Хрупкие тесты (flaky tests) снижают доверие к автоматизации
  • Масштабирование ручного подхода — невозможно
Цель: разработать метод, который автоматически определяет, какие элементы интерфейса изменились между версиями, с высокой точностью и объяснимостью результатов.

Существующие подходы и ограничения

Подход Принцип Ограничения
Попиксельное сравнение Побитовая разница скриншотов Ложные срабатывания при рендеринге шрифтов, динамическом контенте
DOM-diff (tree edit distance) Расстояние редактирования деревьев O(n^3) сложность, не учитывает визуальный контекст
Локальный жадный поиск Greedy matching ближайших элементов Неустойчив при перестановках, каскадные ошибки
CSS-селекторы Сопоставление по пути в DOM Хрупкие при рефакторинге разметки
ML-подходы (CNN) Обучение на парах скриншотов Требуют больших датасетов, black-box, низкая интерпретируемость
Ключевой недостаток: существующие методы либо не учитывают многофакторную природу UI-элементов, либо используют локальный жадный поиск, который дает неоптимальные сопоставления при перестановках элементов.

Вход

Два состояния веб-страницы: baseline (эталон) и current (текущая версия). Для каждого элемента извлекается вектор из 5 групп признаков.

Выход

Список изменений с типами: SELECTOR_CHANGE, CONTENT_CHANGE, REMOVED, ADDED — каждое с оценкой уверенности и рекомендуемым действием.

Извлечение признаков элементов

Каждый интерактивный элемент DOM представляется вектором VectorFingerprint из 5 групп признаков:

Текст (w = 0.32)

Видимый текст элемента. Fuzzy-сравнение: Levenshtein + N-gram. Детекция динамического контента (даты, числа, валюты).

Атрибуты (w = 0.32)

data-testid, id, class, aria-*, role. Иерархия весов: приоритет тестовым атрибутам. Fuzzy matching для классов.

Структура (w = 0.18)

Тег родителя, глубина вложенности, индекс среди соседей, текст предшествующего элемента.

Тег (w = 0.12)

Тип HTML-элемента с учетом семантической близости: BUTTON ~ A, SPAN ~ DIV, INPUT ~ TEXTAREA.

Геометрия (w = 0.06)

Bounding box, площадь относительно viewport. Толерантность 20% для адаптивного дизайна.

Текстовое сходство элементов

Три стратегии сравнения

  • Levenshtein distance — для строк > 20 символов, нормализованное расстояние редактирования
  • N-gram similarity — для коротких строк (≤ 20 символов), коэффициент Жаккара по биграммам
  • Детекция динамического контента — даты, числа, валюты автоматически получают score = 0.85

Комбинирование

Для коротких строк: среднее Levenshtein и N-gram. Это повышает устойчивость к мелким изменениям.

Принцип

Глобальное двудольное сопоставление

Алгоритм Венгера (Куна-Манкреса)

  • Задача назначения: найти оптимальное одно-к-одному соответствие между элементами baseline и current
  • Матрица стоимости: C[i][j] = 1 - S(ei, ej) — инвертированная оценка сходства
  • Сложность: O(n^3), где n — число элементов на странице
  • Практически: ~25ms для страницы с 50 элементами

Преимущества перед жадным поиском

  • Устойчивость к перестановкам — элементы, поменявшие порядок, корректно сопоставляются
  • Отсутствие каскадных ошибок — одно неверное сопоставление не «сдвигает» остальные
  • Математическая оптимальность — минимизирует суммарную стоимость назначений

Обнаружение смещений контейнеров

Проблема

Когда контейнер сдвигается, все вложенные элементы тоже меняют координаты. Без учета этого — каждый дочерний элемент ошибочно помечается как «изменившийся».

Решение: DBSCAN-кластеризация

  • Для каждого контейнера вычисляются смещения (dx, dy) дочерних элементов
  • DBSCAN кластеризует смещения (eps = 10px)
  • Если ≥ 70% детей имеют одинаковое смещение — это сдвиг контейнера
  • Минимальный порог: 3px (подавление шума)

До и после

Без коррекции:
Container margin: 0 → 50px
Button A — CHANGED (dx=50)
Button B — CHANGED (dx=50)
Input C — CHANGED (dx=50)
Итого: 3 ложных срабатывания
С коррекцией (DBSCAN):
Кластер: {dx=50, dy=0}, 3/3 = 100%
Container — SHIFT_DETECTED
Button A — OK (offset compensated)
Button B — OK
Итого: 0 ложных срабатываний

Калибровка уверенности и выбор порога

Трехуровневая калибровка

УровеньScoreДействие
Высокая ≥ threshold + 0.15 Автоматическое обновление селектора
Средняя ≥ threshold Рекомендация обновления с пометкой для проверки
Низкая < threshold Ручной просмотр (MANUAL_REVIEW)

Выбор порога по F1

  • Для каждого типа элемента подбирается порог, максимизирующий F1-меру
  • Баланс между precision и recall: минимизация и ложных срабатываний, и пропусков
  • Пороги валидированы на синтетических и реальных данных

Классификация изменений

SELECTOR_CHANGE

Селектор элемента изменился. Требуется обновление тестов.

CONTENT_CHANGE

Содержимое изменилось, селектор тот же. Проверить ожидаемые значения.

POSSIBLY_REMOVED

Низкая уверенность в совпадении. Элемент возможно удален.

REMOVED

Элемент не найден в текущей версии. Score = 0.

Экспериментальная часть: методика

Синтетические мутации DOM

  • Текстовые — замена, добавление, удаление текста
  • Атрибутные — переименование классов, id, data-*
  • Структурные — перемещение, вложение, перестановка
  • Геометрические — сдвиг, изменение размера, скрытие
  • Комбинированные — несколько типов одновременно

Метрики оценки

  • Precision — доля верных среди найденных совпадений
  • Recall — доля найденных среди реальных совпадений
  • F1-мера — гармоническое среднее precision и recall
  • Accuracy — общая точность классификации
